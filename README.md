# Initial Setup Guide

This guide walks through the initial setup of the PostgreSQL project.

## Prerequisites

Ensure the following software is installed:

* Docker Engine
* Docker Compose (v2+)
* Bash
* Git

Verify the installation:

```bash
docker --version
docker compose version
git --version
```

## Project Structure

After cloning the repository, the project should have the following structure:

```text
project/
├── conf/
│   ├── postgresql.conf
│   ├── pg_hba.conf
│   └── pgbackrest.conf          # Generated by setup.sh
│
├── data/                        # PostgreSQL data directory
├── logs/                        # PostgreSQL & pgBackRest logs
├── wal-archive/                 # WAL archive (local spool)
├── pgbackrest-spool/            # pgBackRest async spool
│
├── initdb/
│   └── *.sql
│
├── scripts/
│   ├── setup.sh
│   ├── start.sh
│   ├── stanza-create.sh
│   ├── backup-full.sh
│   ├── backup-diff.sh
│   ├── backup-expire.sh
│   ├── restore.sh
│   └── benchmark.sh
│
├── docker-compose.yml
├── .env
└── README.md
```

## Make Scripts Executable

Grant execute permission to all shell scripts:

```bash
chmod +x scripts/*.sh
```

Verify:

```bash
ls -l scripts/
```

Example:

```text
-rwxr-xr-x setup.sh
-rwxr-xr-x start.sh
-rwxr-xr-x stop.sh
...
```

## Configure Environment

Edit the `.env` file before running the setup.

Typical settings include:

* PostgreSQL version
* PostgreSQL password
* pgBackRest S3 configuration
* MinIO endpoint
* PMM configuration

Example:

```bash
cp .env-example .env
nano .env
```

## Run Initial Setup

Execute the setup script:

```bash
./scripts/setup.sh
```

The setup script will:

* Verify Docker is installed
* Verify the PostgreSQL image
* Verify pgBackRest is available
* Create the required directories
* Generate `conf/pgbackrest.conf`
* Configure directory permissions
* Display a setup summary

# Host OS Tuning

Before deploying PostgreSQL, tune the Linux kernel parameters for better database performance.

## Configure sysctl

Edit the sysctl configuration file:

```bash
sudo nano /etc/sysctl.conf
```

Add the following parameters:

```conf
# -----------------------------------------------------------------------------
# PostgreSQL Performance Tuning
# -----------------------------------------------------------------------------

# Reduce swapping
vm.swappiness = 1

# Dirty page writeback
vm.dirty_background_ratio = 5
vm.dirty_ratio = 15

# Shared memory
kernel.shmmax = 17179869184
kernel.shmall = 4194304
```

Or create a dedicated configuration file:

```bash
sudo tee /etc/sysctl.d/99-postgresql.conf >/dev/null <<EOF
# PostgreSQL Performance Tuning

vm.swappiness=1
vm.dirty_background_ratio=5
vm.dirty_ratio=15

kernel.shmmax=17179869184
kernel.shmall=4194304
EOF
```

Reload the kernel parameters:

```bash
sudo sysctl --system
```

Verify the configuration:

```bash
sysctl vm.swappiness
sysctl vm.dirty_background_ratio
sysctl vm.dirty_ratio
sysctl kernel.shmmax
sysctl kernel.shmall
```

Expected output:

```text
vm.swappiness = 1
vm.dirty_background_ratio = 5
vm.dirty_ratio = 15
kernel.shmmax = 17179869184
kernel.shmall = 4194304
```

## Parameter Description

| Parameter                   |           Recommended | Description                                                        |
| --------------------------- | --------------------: | ------------------------------------------------------------------ |
| `vm.swappiness`             |                   `1` | Minimizes swapping and keeps PostgreSQL memory in RAM.             |
| `vm.dirty_background_ratio` |                   `5` | Starts background flushing when 5% of memory contains dirty pages. |
| `vm.dirty_ratio`            |                  `15` | Forces dirty pages to be written when 15% of memory is dirty.      |
| `kernel.shmmax`             | `17179869184` (16 GB) | Maximum size of a shared memory segment.                           |
| `kernel.shmall`             |             `4194304` | Total shared memory pages available to the system.                 |

## Notes

* These values are appropriate for a server with **32 GB RAM**.
* If the server memory changes, adjust `kernel.shmmax` and `kernel.shmall` accordingly.
* A system reboot is **not required** after running `sysctl --system`.

# Backup

## Automatic Backup Schedule

Backups are scheduled on the **host** using `cron`. The `pgbackrest` container does not run a cron daemon.

Edit the root crontab:

```bash
sudo crontab -e
```

Add the following entries:

```cron
# Weekly Full Backup (Sunday 01:00)
0 1 * * 0 /path/to/postgresql/scripts/backup-full.sh >> /var/log/pgbackrest.log 2>&1

# Daily Differential Backup (Monday-Saturday 01:00)
0 1 * * 1-6 /path/to/postgresql/scripts/backup-diff.sh >> /var/log/pgbackrest.log 2>&1

# Cleanup Expired Backups (Daily 03:00)
0 3 * * * /path/to/postgresql/scripts/backup-expire.sh >> /var/log/pgbackrest.log 2>&1
```

Replace `/path/to/postgresql` with your PostgreSQL project directory.

Example:

```cron
0 1 * * 0 ~/postgresql/scripts/backup-full.sh >> /var/log/pgbackrest.log 2>&1
0 1 * * 1-6 ~/postgresql/scripts/backup-diff.sh >> /var/log/pgbackrest.log 2>&1
0 3 * * * ~/postgresql/scripts/backup-expire.sh >> /var/log/pgbackrest.log 2>&1
```

# PostgreSQL Restore Guide

This document explains how to use the PostgreSQL restore scripts based on **pgBackRest** and **Docker Compose**.

## Prerequisites

Before performing a restore, ensure:

* Docker and Docker Compose are installed.
* PostgreSQL container is configured correctly.
* `pgbackrest.conf` points to the correct backup repository.
* The repository contains a valid stanza and backups.
* The PostgreSQL container is named `postgres`.


## Restore Workflow

The recommended restore workflow is:

```text
restore-info.sh
        │
        ▼
restore-precheck.sh
        │
        ▼
Choose Restore Method
        │
        ├── restore-latest.sh
        ├── restore-time.sh
        ├── restore-point.sh
        └── restore-set.sh
        │
        ▼
restore-verify.sh
        │
        ▼
docker compose up -d postgres
```


## Script Overview

| Script                | Description                                                               |
| --------------------- | ------------------------------------------------------------------------- |
| `restore-info.sh`     | Display repository information and available backups.                     |
| `restore-precheck.sh` | Validate repository health before restoring.                              |
| `restore-latest.sh`   | Restore the latest backup.                                                |
| `restore-time.sh`     | Restore to a specific timestamp (Point-in-Time Recovery).                 |
| `restore-point.sh`    | Restore to a named restore point.                                         |
| `restore-set.sh`      | Restore a specific backup set.                                            |
| `restore-verify.sh`   | Verify the restored PostgreSQL data directory before starting PostgreSQL. |



## 1. View Available Backups

Display repository information.

```bash
./scripts/restore-info.sh
```

Example:

```text
stanza: main

status: ok

full backup:
    20260729-010001F

diff backup:
    20260730-010001D

wal archive:
    min/max ...
```

Use this command whenever you need to know which backup sets are available.


## 2. Verify Repository

Verify the repository before restoring.

```bash
./scripts/restore-precheck.sh
```

This command checks:

* Repository connectivity
* Repository configuration
* Archive accessibility
* Stanza validity

If this command reports an error, do **not** continue with the restore until the issue has been resolved.


## 3. Restore the Latest Backup

Restore the newest backup available.

```bash
./scripts/restore-latest.sh
```

The script automatically:

1. Stops PostgreSQL.
2. Confirms deletion of the existing data directory.
3. Removes the old database files.
4. Restores the latest backup.

Use this option for disaster recovery when the latest backup should be restored.


## 4. Restore to a Specific Time

Restore using Point-in-Time Recovery (PITR).

```bash
./scripts/restore-time.sh "2026-07-29 14:30:00"
```

Example:

```bash
./scripts/restore-time.sh "2026-07-29 18:15:00"
```

This restores the database to the specified timestamp using archived WAL files.

Use this option when:

* Recovering from accidental DELETE or UPDATE operations.
* Recovering before application deployment.
* Recovering before data corruption.


## 5. Restore to a Named Restore Point

Restore to a previously created restore point.

Example:

```sql
SELECT pg_create_restore_point('before_upgrade');
```

Restore:

```bash
./scripts/restore-point.sh before_upgrade
```

Use this method before:

* Major upgrades
* Data migrations
* Schema changes
* Application deployments


## 6. Restore a Specific Backup Set

Restore an exact backup set.

Example:

```bash
./scripts/restore-set.sh 20260729-010001F
```

The backup set identifier can be obtained from:

```bash
./scripts/restore-info.sh
```

This option is useful when multiple full backups exist and a specific backup must be restored.


## 7. Verify the Restored Database

After a restore completes, verify the restored data directory.

```bash
./scripts/restore-verify.sh
```

Typical output:

```text
✓ PG_VERSION
✓ backup_label
✓ recovery.signal
✓ postgresql.auto.conf
✓ pg_wal
✓ Repository reachable

Restore verification PASSED
```

If any required file is missing, the script reports the failure before PostgreSQL is started.


## Start PostgreSQL

Once verification succeeds:

```bash
docker compose up -d postgres
```

Monitor the logs:

```bash
docker compose logs -f postgres
```

Wait until PostgreSQL reports:

```text
database system is ready to accept connections
```


## Typical Recovery Scenarios

### Restore After Hardware Failure

```bash
./scripts/restore-info.sh
./scripts/restore-precheck.sh
./scripts/restore-latest.sh
./scripts/restore-verify.sh
docker compose up -d postgres
```


### Recover Deleted Data

```bash
./scripts/restore-info.sh
./scripts/restore-precheck.sh
./scripts/restore-time.sh "2026-07-29 15:30:00"
./scripts/restore-verify.sh
docker compose up -d postgres
```


### Recover Before Application Upgrade

```bash
./scripts/restore-point.sh before_upgrade
./scripts/restore-verify.sh
docker compose up -d postgres
```


### Restore a Historical Backup

```bash
./scripts/restore-info.sh
./scripts/restore-set.sh 20260721-010001F
./scripts/restore-verify.sh
docker compose up -d postgres
```


## Best Practices

* Always execute `restore-precheck.sh` before restoring.
* Always execute `restore-verify.sh` before starting PostgreSQL.
* Do not modify `pgbackrest.conf` or `repo1-path` during recovery.
* Ensure the repository configuration used during restore matches the configuration used to create the backup.
* Verify that archived WAL files are available when performing Point-in-Time Recovery.
* Monitor PostgreSQL logs after startup to confirm recovery completes successfully.
* Perform periodic test restores to validate backup integrity.


## Complete Restore Lifecycle

```text
1. Inspect available backups

    ./scripts/restore-info.sh

            │

2. Validate repository

    ./scripts/restore-precheck.sh

            │

3. Perform restore

    Latest Backup
        ./scripts/restore-latest.sh

    Point-in-Time
        ./scripts/restore-time.sh "YYYY-MM-DD HH:MM:SS"

    Restore Point
        ./scripts/restore-point.sh before_upgrade

    Backup Set
        ./scripts/restore-set.sh BACKUP_SET

            │

4. Verify restored cluster

    ./scripts/restore-verify.sh

            │

5. Start PostgreSQL

    docker compose up -d postgres

            │

6. Verify PostgreSQL startup

    docker compose logs -f postgres
```

# Percona Monitoring and Management (PMM)

This section describes how to create a dedicated PostgreSQL monitoring user and register the database with a PMM Server.

## Create PMM Monitoring User

Connect to PostgreSQL:

```bash
docker exec -it postgres psql -U postgres
```

Create a dedicated monitoring user.

Replace `CHANGE_ME` with a strong password.

```sql
CREATE ROLE pmm LOGIN PASSWORD 'CHANGE_ME';

GRANT pg_monitor TO pmm;
GRANT pg_read_all_stats TO pmm;
GRANT pg_read_all_settings TO pmm;
GRANT pg_read_all_data TO pmm;
```

Grant CONNECT permission to every existing database.

```sql
DO
$$
DECLARE
    db RECORD;
BEGIN
    FOR db IN
        SELECT datname
        FROM pg_database
        WHERE datistemplate = false
    LOOP
        EXECUTE format(
            'GRANT CONNECT ON DATABASE %I TO pmm;',
            db.datname
        );
    END LOOP;
END;
$$;
```

Verify:

```sql
\du
```

Expected output:

```
Role name | Attributes
----------+------------------------------
pmm       | Login
```

Exit PostgreSQL:

```sql
\q
```

## Configure PMM Client

Edit the `.env` file.

```dotenv
PMM_SERVER_IP=192.168.10.100
PMM_SERVER_USER=admin
PMM_SERVER_PASSWORD=CHANGE_ME

```

## Start PMM Client

```bash
docker compose up -d pmm-client
```

Verify the container is running.

```bash
docker compose ps
```

## Register PostgreSQL with PMM Server

Register the database:

```bash
docker exec pmm-client \
pmm-admin add postgresql \
    --username=pmm \
    --password=CHANGE_ME \
    --host=postgres \
    --port=5432 \
    --database=postgres \
    --service-name=postgresql \
    --query-source=pgstatmonitor
```

If `pgstatmonitor` is not installed, use:

```bash
docker exec pmm-client \
pmm-admin add postgresql \
    --username=pmm \
    --password=CHANGE_ME \
    --host=postgres \
    --port=5432 \
    --database=postgres \
    --service-name=postgresql
```

## Verify Registration

Check PMM client status:

```bash
docker exec pmm-client pmm-admin status
```

Example:

```
Agent ID      : ...
Node ID       : ...
Node name     : postgres-node
PMM Server    : https://192.168.10.100
```

List monitored services:

```bash
docker exec pmm-client pmm-admin list
```

Expected output:

```
Service type    : PostgreSQL
Service name    : postgresql
Address         : postgres:5432
```

## Verify from PMM Server

Open the PMM web interface.

```
https://<PMM_SERVER_IP>
```

Navigate to:

```
Inventory
    └── Services
```

Verify:

- PostgreSQL service is **Up**
- Node status is **Online**
- Metrics are being collected

Then open:

```
Dashboards
    └── PostgreSQL
```

Verify:

- Connections
- Transactions
- WAL Activity
- Replication
- Buffer Cache
- Checkpoints
- Query Analytics

are reporting data.

## Check PMM Client Logs

```bash
docker compose logs -f pmm-client
```

## Check Agent Status

```bash
docker exec pmm-client pmm-admin status
```

## Remove Registration

```bash
docker exec pmm-client \
pmm-admin remove postgresql postgresql
```

## Register Again

```bash
docker exec pmm-client \
pmm-admin add postgresql \
    --username=pmm \
    --password=CHANGE_ME \
    --host=postgres \
    --port=5432 \
    --database=postgres \
    --service-name=postgresql \
    --query-source=pgstatmonitor
```

## Security Recommendations

- Use a dedicated monitoring user (`pmm`).
- Never use the `postgres` superuser for monitoring.
- Store credentials only in the `.env` file.
- Use a strong password for the PMM monitoring user.
- Restrict network access to the PMM Server.
- Enable HTTPS for all PMM communications.

# Benchmark Guide

This document explains how to use `scripts/benchmark.sh` to benchmark your PostgreSQL server using **pgbench**.

## Overview

The benchmark script automatically:

* Verifies the PostgreSQL container is running.
* Verifies `pgbench` is installed.
* Initializes the `pgbench` tables (first run only).
* Performs a warm-up benchmark.
* Runs multiple benchmark workloads.
* Collects PostgreSQL configuration.
* Collects PostgreSQL statistics.
* Saves all results to a timestamped log file.

The benchmark runs **inside the PostgreSQL container**, so no PostgreSQL client tools are required on the host.

## Requirements

* Docker
* Running PostgreSQL container
* `pgbench` installed inside the PostgreSQL container
* PostgreSQL user with permission to create tables

Default container name:

```text
postgres
```

If your container has another name, specify it using:

```bash
POSTGRES_CONTAINER=my-postgres
```

## Benchmark Directory

Benchmark results are stored in:

```text
benchmark/
```

Example:

```text
benchmark/
└── pgbench_20260729_103000.log
```

## First Benchmark

The first execution must initialize the pgbench tables.

```bash
INIT=true ./scripts/benchmark.sh
```

This command creates the following tables:

* pgbench_accounts
* pgbench_branches
* pgbench_history
* pgbench_tellers

After initialization, the script performs:

* VACUUM ANALYZE
* Warm-up
* Benchmark tests

## Subsequent Benchmarks

After initialization, simply run:

```bash
./scripts/benchmark.sh
```

The script automatically detects the existing pgbench tables and skips initialization.

## Environment Variables

## Container

Default:

```bash
POSTGRES_CONTAINER=postgres
```

Example:

```bash
POSTGRES_CONTAINER=postgres-prod ./scripts/benchmark.sh
```
## Database User

Default:

```bash
PGUSER=postgres
```

Example:

```bash
PGUSER=myuser ./scripts/benchmark.sh
```

## Database

Default:

```bash
PGDATABASE=postgres
```

Example:

```bash
PGDATABASE=benchmark ./scripts/benchmark.sh
```

## Scale Factor

Default:

```bash
SCALE=100
```

Larger values generate larger datasets.

Example:

```bash
SCALE=1000 ./scripts/benchmark.sh
```

Approximate database sizes:

| Scale | Size    |
| ----: | ------- |
|   100 | ~1.5 GB |
|   500 | ~7 GB   |
|  1000 | ~15 GB  |
|  5000 | ~75 GB  |


## Benchmark Duration

Default:

```bash
TIME=300
```

Example:

```bash
TIME=600 ./scripts/benchmark.sh
```

Runs each benchmark for 10 minutes.

## Client Counts

Default:

```bash
CLIENTS="8 16 32 64"
```

Example:

```bash
CLIENTS="16 32 64 128" ./scripts/benchmark.sh
```

The script automatically selects an appropriate number of worker threads (`-j`) based on the client count.

## Example

Run a larger benchmark:

```bash
SCALE=1000 \
TIME=600 \
CLIENTS="32 64 128" \
./scripts/benchmark.sh
```

## Benchmark Workflow

The script performs the following steps:

1. Verify Docker container.
2. Verify `pgbench`.
3. Display PostgreSQL version.
4. Display pgbench version.
5. Record PostgreSQL configuration.
6. Initialize pgbench tables (if required).
7. Run `VACUUM ANALYZE`.
8. Execute a 60-second warm-up.
9. Run benchmarks for each client count.
10. Collect PostgreSQL statistics.
11. Save results.


## Understanding the Results

Typical pgbench output:

```text
transaction type: <builtin: TPC-B>
scaling factor: 100
clients: 32
threads: 8
duration: 300 s

latency average = 4.10 ms

tps = 7800.42 (without initial connection time)
```

Key metrics:

| Metric  | Description                                   |
| ------- | --------------------------------------------- |
| TPS     | Transactions per second. Higher is better.    |
| Latency | Average transaction latency. Lower is better. |
| Clients | Number of concurrent database connections.    |
| Threads | Number of pgbench worker threads.             |


## Recommended Test Procedure

For consistent and comparable results:

1. Restart PostgreSQL if testing configuration changes.
2. Wait until PostgreSQL is fully started.
3. Ensure no other workloads are running.
4. Run the benchmark at least three times.
5. Compare the average TPS and latency.


## Reinitialize the Benchmark Dataset

To recreate the benchmark tables:

```bash
INIT=true ./scripts/benchmark.sh
```

This recreates the pgbench dataset using the current `SCALE` value.

## Log Files

Each benchmark run generates a timestamped log:

```text
benchmark/
├── pgbench_20260729_090001.log
├── pgbench_20260729_140015.log
└── pgbench_20260730_100500.log
```

The log includes:

* PostgreSQL version
* pgbench version
* PostgreSQL configuration
* Benchmark output
* PostgreSQL statistics
* TPS
* Latency
* Execution timestamps

## Performance Tips

For production-grade benchmarking:

* Disable other workloads during testing.
* Use a dedicated benchmark database.
* Test multiple client counts.
* Run tests with realistic data volumes.
* Compare results after each PostgreSQL tuning change.
* Monitor CPU, memory, disk I/O, and network utilization alongside the benchmark results.
